tsdg-ai-backend Build Plan

Taisandaugia's real system is a .NET 10 backend (Auction-Project) and an Angular 19 frontend (auction-platform), with no AI code in it at all. The four workflows W1–W4 run only on a React/Supabase prototype with simulated AI, which is what settled the business rules. This document proposes that ORT build a separate AI service on the renchan stack, called by the .NET backend over REST, with the contract for all four workflows fixed now.

01 · Summary

What ORT builds, and on which pattern

  • One new repository, tsdg-ai-backend (Node ESM, renchan). Two processes as in rgp-yazaki: PROC-01 the REST API and PROC-02 the BullMQ worker. Taisandaugia's .NET backend calls in over REST with an HMAC signature; ORT never writes to taisandaugia's PostgreSQL.
  • Five services, each a ProceduralAgentLoop: the step order is fixed in code, the AI only judges inside a step through one forced tool call, and every output is re-checked by code (the recordFieldValues pattern from leepai).
  • The document-reading layer is ported from rgp-yazaki: every read value carries the envelope {value, pageNumber, region}, each document is read N times and settled by absolute majority, every file handed to a provider is recorded, and the AI driver defaults to the stub in every environment.
  • The multi-provider layer is ported from leepai: BaseAiModelProcessor → provider base → one processor per model, with model, prompt and tool schema held as DB data with _bk history.
  • Confidence is computed by code from observed signals (agreement across readings, evidence kind, validation outcome), never taken from a number the model declares. That keeps taisandaugia's High / Medium / Check bands and its auto-send threshold without breaking ORT's "the AI never judges" rule.
  • Every run is asynchronous: 202 plus a runKey, the result pushed back on a signed callback, with GET for reconciliation.

02 · Context

Responsibility boundary

The real system. Backend Auction-Project: .NET 10 Clean Architecture (Domain / Application / Infrastructure / Web), MediatR plus FluentValidation, EF Core on PostgreSQL with hand-written SQL migrations, JWT bearer, files on Cloudflare R2 (table uploaded_files, read URLs signed at read time), pay-per-run credits (PaywallPurchaseService), Kafka for email and tracking, running under systemd on a single VPS. Frontend auction-platform: Angular 19 standalone, with the asset-owner portal carrying the five-step digitisation wizard, the organisation portal and the admin area. No LLM SDK, no durable job queue, and no webhook that verifies a signature.

The prototype taisandaugia (React + Supabase) runs all of W1–W4 with simulated AI: the wizard's AI extraction button, consignment quotes and contracts, org-created auction sessions, the outreach pack, case documents, and Q&A with a citation gate. Most of it does not exist in the real system; porting it is taisandaugia's work and is discussed separately. This document takes the business rules from the prototype (result shapes, the citation gate, preserving hand edits) so the AI contract can be settled now.

So ORT builds no screens, no statuses and no business gates. ORT receives the full context in each request and returns structured results; the .NET backend decides what to store and what to show.

04 · Architecture

How one request travels

  1. Someone presses a button in Angular — for example "Extract with AI" on step 2 of the digitisation wizard.
  2. The .NET API (a MediatR command) checks the JWT, KYC and permissions (AssetPostingGuard, MeOrganizationGuard), charges credits, writes one ai_run_requests row as pending and returns its id immediately. An outbox-style hosted service picks the pending row up, mints time-limited R2 URLs (IFileStorageService.GetReadUrlAsync) and calls ORT with the HMAC signature and an Idempotency-Key.
  3. ORT's renderer validates the body, creates ai_runs in a transaction and only after commit dispatches the job (hor-execution-placement-pattern §2.1), returning 202.
  4. The worker runs the service's agent loop: fetch media first, read N times through the processor, normalize, settle consensus, score confidence. Every model call writes one ai_model_calls row, and every step boundary emits progress.
  5. The result is stored on the run and the callback delivery job is dispatched.
  6. The callback POSTs to .NET's OrtCallbackController, signed; a network failure is retried with growing delay. Delivering a callback costs no model money, so it retries — calling a model does not.
  7. .NET verifies the signature over the raw body, skips a runKey it has already processed, writes the result into ai_run_requests (and refunds credits when the run ended failed or cancelled). Angular polls GET api/me/ai-runs/{id} on the CreditPaymentPollingService pattern until a terminal state.
  8. A reconciliation hosted service calls GET /v1/ai-runs/:runKey for runs stuck longer than five minutes.
ADR-01A separate AI service rather than AI code inside the .NET backend. Reasons: it reuses ORT's whole AI layer (multi-provider processors, agent loop, stub, egress record, test suite); .NET today has no LLM SDK, no durable job queue and no retry policy; the model API keys stay out of .NET's appsettings, which is committed to git; and token spend is measured in exactly one place.
ADR-02REST v1 (renderers) rather than GraphQL. The caller is a .NET server using a typed HttpClient, not an SPA; hor-execution-placement-pattern §3 places inbound integration from another system in a renderer. There is no end-user surface and no public endpoint.
ADR-03Every run is asynchronous, W4b included. An AI call is heavy work and belongs in a worker. The .NET side holds no HTTP request open waiting for it: the frontend already has a polling pattern (payment QR, every 4 seconds), so a few seconds of latency changes nothing for the user.

Authentication and idempotency

  • Headers x-ort-client-id, x-ort-timestamp (epoch seconds, 300-second window) and x-ort-signature = hex HMAC-SHA256 over timestamp + "." + rawBody. The REST engine already keeps request.rawBody (linoa's AppRestfulApiServerEngine).
  • Verified in AppRestfulApiContext.findUser, which resolves an ApiClient (linoa already sketches get provider()). The secret is stored encrypted under API_CLIENT_SECRET_ENCRYPTION_KEY; two secrets stay valid during a rotation.
  • Callbacks are signed the same way with an added x-ort-run-key header. The .NET side has to read the raw body to verify it (Request.EnableBuffering() before model binding); no helper exists there today, and the Casso/SePay webhooks currently verify nothing.
  • Idempotency-Key is required — the ai_run_requests id is the natural choice; the same key with a different body returns 409.

05b · Operations

Observing and controlling a run

This whole section was added after the 17 Sep review. The principle: anything written to the database must be readable back, anything running must be visible, and anything running must be stoppable.

Step trace · F-1

Today only AI steps leave a mark (ai_model_calls). When a CODE step drops a value — path outside the schema, option not in the list, over the length, no absolute majority — the result only shows that the field is gone. From now on every step writes a row.

FR-TRC-02When a CODE step rejects a value, that value and a reason code are recorded. Applies to AssetFieldValueNormalizer, FieldConsensusResolver, LegalFieldEnvelopeNormalizer, CaseClauseNormalizer, OutreachFieldGuard, CitationQuoteVerifier.

Admin console · FR-ADM

Settled on 18 Sep with OPEN-05: ORT runs on its own VPS, operates the service, and builds an admin console that taisandaugia staff are given accounts on. This is the first time ORT holds a human identity — everything else in this document is machine-to-machine — which is what makes it a separate piece of work rather than a screen.

IDRequirement
FR-ADM-01One console, two roles. A taisandaugia user sees only runs belonging to their own ApiClient; an ORT operator reads across clients and so answers FR-LST-03. Building both at once costs one role flag and one unscoped query; bolting the second on later costs a rewrite of every query.

Decision · 18 SepApproval is a run boundary, not a pause inside a run. The alternative was a run that halts at a step boundary, enters a non-terminal awaiting_approval state and continues through a resume endpoint. It was rejected, for four reasons.

1 · Nothing in scope needs it. Of the five services, only one has a person standing between two AI steps: AI-W4a → staff confirm clauses → AI-W4b. In the other four the person stands at the end, with no AI step after them. What crosses that one gap is the confirmed clause list — small text, and already the specified input to W4b, which never re-reads the PDF. So the usual argument for suspending, that re-sending the intermediate state is expensive, does not apply anywhere.

2 · The pause is unbounded. A person may decide in two minutes or in three days. RUN_TIME_LIMIT_SECONDS=300, the worker’s kill_timeout, the BullMQ job and the 30-day content clock all assume a run is short; suspending makes run duration a quantity measured in working days.

3 · Credits. Billing is per run. A suspended run holds a charge in limbo — charged or not, refunded on abandonment or not — while wallet_refunds on the .NET side is still scaffolding nothing writes to. Two runs are charged twice, which is also the honest answer: two runs consumed two sets of model calls.

4 · awaiting_approval is business state, which ADR-05 keeps out of ORT. It means “a person owes us a decision”, and it belongs next to who approved and what they edited. Splitting it across two systems would split the audit trail for a single approval — the thing 24-month trace retention exists to prevent.

Choosing this now does not foreclose the other: a suspend-and-resume state can be added later if a workflow ever needs approval inside an expensive computation whose intermediate state is costly to rebuild. Choosing the other now would cost P0, the phase everything else waits on.

One workflow is not one run. The user must never see two. When taisandaugia records the approval it dispatches run 2 immediately; correlationId groups the chain in API-R002, and the wizard shows one progress line. The split exists in the contract between two servers, not on anyone’s screen.

11 · Quality

Testing and evaluation

The suite (runs on the stub: no key, no egress)

  • tests/__tests__/, no database writes: normalizers, verifiers, consensus, confidence scorers, actions (ActionContractAssertion), processors against fake capsules. Written as test.each case tables.
  • tests/_orders/, database writes: renderers (idempotency, 409, HMAC), the worker (status transitions, ai_model_calls written), the callback job.
  • tests/fixtures/sharedCitationCases.json: the citation case table. When taisandaugia ports the gate to C#, their xUnit tests read the same file; a divergence turns the suite red on both sides.
  • A smoke test against a running host: submit all five run kinds, wait for the callbacks, assert provider_uploaded_files is empty in stub mode; cancel a running run and assert a cancelled callback; read ?expand=steps back and check the step count.
  • Tests for the post-review additions: one case per rejection reason code; cancelling a queued run costs zero model calls; cancelling a terminal run returns that state; out-of-order progress events are ignored by the receiver; and after simulating a content purge, the trace still answers "why is this field missing".

01 · Tóm tắt

ORT xây cái gì, và theo pattern nào

  • Một repository mới, tsdg-ai-backend (Node ESM, renchan). Hai process như ở rgp-yazaki: PROC-01 là REST API và PROC-02 là worker BullMQ. Backend .NET của Taisandaugia gọi sang qua REST kèm chữ ký HMAC; ORT không bao giờ ghi vào PostgreSQL của taisandaugia.
  • Năm dịch vụ, mỗi dịch vụ là một ProceduralAgentLoop: thứ tự các bước cố định trong code, AI chỉ phán đoán bên trong một bước thông qua một tool call bắt buộc, và mọi output đều được code kiểm tra lại (pattern recordFieldValues từ leepai).
  • Lớp đọc tài liệu được port từ rgp-yazaki: mọi giá trị đọc được đều mang envelope {value, pageNumber, region}, mỗi tài liệu được đọc N lần và chốt bằng đa số tuyệt đối, mọi file giao cho provider đều được ghi nhận, và driver AI mặc định là stub ở mọi môi trường.
  • Lớp multi-provider được port từ leepai: BaseAiModelProcessor → lớp base của provider → mỗi model một processor, với model, prompt và tool schema lưu dưới dạng dữ liệu DB kèm lịch sử _bk.
  • Độ tin cậy do code tính ra từ các tín hiệu quan sát được (mức đồng thuận giữa các lần đọc, loại bằng chứng, kết quả kiểm tra), không bao giờ lấy từ con số mà model tự khai. Nhờ vậy vẫn giữ được các dải Cao / Trung bình / Cần kiểm tra của taisandaugia và ngưỡng tự động gửi, mà không phá vỡ nguyên tắc "AI không bao giờ quyết định" của ORT.
  • Mọi run đều bất đồng bộ: trả 202 kèm một runKey, kết quả được đẩy ngược về qua callback có chữ ký, kèm GET để đối soát.

04 · Kiến trúc

Hành trình của một request

  1. Một người nhấn nút trong Angular — ví dụ "Extract with AI" ở bước 2 của wizard số hoá.
  2. .NET API (một MediatR command) kiểm JWT, KYC và quyền (AssetPostingGuard, MeOrganizationGuard), trừ credit, ghi một dòng ai_run_requests ở trạng thái pending rồi trả id về ngay. Một hosted service kiểu outbox lấy dòng pending đó, sinh URL R2 có hạn (IFileStorageService.GetReadUrlAsync) và gọi ORT kèm chữ ký HMAC cùng một Idempotency-Key.
  3. Renderer của ORT kiểm tra body, tạo ai_runs trong một transaction và chỉ dispatch job sau khi commit (hor-execution-placement-pattern §2.1), rồi trả về 202.
  4. Worker chạy agent loop của dịch vụ: tải media trước, đọc N lần qua processor, chuẩn hoá, chốt đồng thuận, chấm độ tin cậy. Mỗi lần gọi model ghi một dòng ai_model_calls, và mỗi ranh giới bước phát ra tiến độ.
  5. Kết quả được lưu vào lần chạy và job gửi callback được dispatch.
  6. Callback POST sang OrtCallbackController của .NET, có ký; lỗi mạng được retry với độ trễ tăng dần. Gửi callback không tốn tiền model nên được retry — còn gọi model thì không.
  7. .NET kiểm chữ ký trên raw body, bỏ qua runKey đã xử lý, ghi kết quả vào ai_run_requests (và hoàn credit khi lần chạy kết thúc ở failed hoặc cancelled). Angular polling GET api/me/ai-runs/{id} theo mẫu CreditPaymentPollingService cho tới khi đạt trạng thái kết thúc.
  8. Một hosted service đối soát gọi GET /v1/ai-runs/:runKey cho những lần chạy kẹt quá năm phút.
ADR-01Tách riêng một dịch vụ AI thay vì nhúng code AI vào backend .NET. Lý do: nó tái dùng toàn bộ lớp AI của ORT (processor đa nhà cung cấp, agent loop, stub, bản ghi egress, bộ test); .NET hiện không có LLM SDK, không có queue job bền vững và không có retry policy; API key của model nằm ngoài appsettings của .NET — file vốn được commit lên git; và chi phí token được đo ở đúng một chỗ.
ADR-02REST v1 (renderer) thay vì GraphQL. Bên gọi là một server .NET dùng HttpClient có kiểu, không phải SPA; hor-execution-placement-pattern §3 đặt phần tích hợp gọi vào từ hệ thống khác trong renderer. Không có giao diện người dùng cuối và không có endpoint công khai.
ADR-03Mọi lần chạy đều bất đồng bộ, kể cả W4b. Một lần gọi AI là việc nặng và thuộc về worker. Phía .NET không giữ request HTTP nào mở để chờ: frontend đã có sẵn mẫu polling (QR thanh toán, mỗi 4 giây), nên vài giây độ trễ không đổi gì với người dùng.

Xác thực và idempotency

  • Các header x-ort-client-id, x-ort-timestamp (giây epoch, cửa sổ 300 giây) và x-ort-signature = HMAC-SHA256 dạng hex trên timestamp + "." + rawBody. REST engine vốn đã giữ request.rawBody (AppRestfulApiServerEngine của linoa).
  • Được kiểm trong AppRestfulApiContext.findUser, nơi phân giải ra một ApiClient (linoa đã phác sẵn get provider()). Secret được lưu mã hoá dưới API_CLIENT_SECRET_ENCRYPTION_KEY; trong lúc xoay vòng thì hai secret cùng có hiệu lực.
  • Callback được ký cùng cách, thêm header x-ort-run-key. Phía .NET phải đọc raw body để kiểm (Request.EnableBuffering() trước khi model binding); hiện bên đó chưa có helper nào, và các webhook Casso/SePay hiện không kiểm gì cả.
  • Idempotency-Key là bắt buộc — id của ai_run_requests là lựa chọn tự nhiên; cùng một key nhưng body khác sẽ trả về 409.
